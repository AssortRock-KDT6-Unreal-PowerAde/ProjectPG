맵 생성 코드 사전

타일맵 생성 코드를 읽으면서 나온 개념들을 그림으로 정리했다. 막히면 여기부터 훑고, 그래도 안 잡히면 그때 물어라.

코드 한 줄 읽는 순서

왼쪽부터 읽으면 안 된다. 순서가 있다.

① = 를 찾는다  →  ② 괄호 안쪽이 먼저  →  ③ = 오른쪽이 실행된다  →  ④ 왼쪽 그릇에 담긴다

int posXRan = gameMode->GenerateRandomNumber(1, _startPositionRangeSize - 1);
순서일어나는 일결과
②_startPositionRangeSize 를 꺼낸다4
②4 - 13
③게임모드한테 “1부터 3까지 중 하나 뽑아줘”1 또는 2 또는 3
④posXRan 그릇에 담는다posXRan = 2

괄호 안 두 숫자는 범위의 양 끝이다. 나오는 값은 하나다.

단, 함수마다 다르다 — RemoveAt(0, 4) 의 4 는 “어디까지”가 아니라 개수다. 함수 이름을 보고 판단해라.

이름이 알려주는 것

함수 이름 앞자리와 접두사만 봐도 뭘 하는지 짐작할 수 있다.

앞자리 = 돌려줄 것의 타입

선언돌려주나어떻게 쓰나
AMapTile* FindTile(...)준다AMapTile* tile = FindTile(...);
ETileType GetType()준다if (tile->GetType() != ...)
bool IsTileARoad(...)준다if (IsTileARoad(x, y))
void SetType(...)안 준다tile->SetType(...);
void Add(...)안 준다_tilesRoad.Add(tile);

void 짜리를 = 로 받으려 하면 안 된다. 줄 게 없다.

x = tile->SetType(...); ✗  ·  tile->SetType(...); ✓

단, void 함수 안에서 = 를 쓰는 건 아무 문제 없다.

접두사 = 하는 일

접두사돌려주는 것바꾸나예
Is~ / Has~ / Can~참 / 거짓안 바꾼다IsTileInBoundary
Get~값안 바꾼다GetType
Set~없음바꾼다SetType
Generate~보통 없음만든다GenerateRoadTile

Get~ 은 들고 있던 값을 그냥 건네는 심부름, Is~ 는 여러 조건을 따져 내리는 판정이다.

상속이냐 소유냐

이 둘을 섞으면 코드 구조가 통째로 안 보인다.

뜻이 프로젝트에서
상속
is-a		 ~는 ~의 일종이다.
자식이 부모 것을 전부 물려받는다.		 AGameModePG 는 AGameMode 다
소유
has-a		 ~가 ~를 들고 있다.
물려받는 게 아니다.		 AGameModePG 가
UMapGeneratorComponent 를 가진다

판별법 — 헤더에 class X : public Y 가 있으면 상속. 전방선언 + 포인터면 무조건 소유다. 상속은 전방선언으로 못 하고 반드시 #include 가 필요하기 때문이다.

그래서 캐스트가 필요하다

UMapGeneratorComponent 는 게임모드를 상속받지 않는다. 다른 집안이다. 그래서 게임모드의 기능을 쓰려면 찾아가야 한다.

UWorld* world = GetWorld();                                          // 세상을 얻고
AGameModePG* gameMode = Cast<AGameModePG>(world->GetAuthGameMode()); // 주인을 찾고
gameMode->GenerateRandomNumber(0, 7);                                // 그제서야 부른다

GetAuthGameMode() 의 반환 타입은 AGameModeBase* 다. 그 타입에는 GenerateRandomNumber, SetRandomSeed, CheckPossibility, GetMapGenerationSeed 가 하나도 없다. 넷 다 AGameModePG 가 새로 만든 것이라 캐스트해서 꺼낸다.

캐스트는 실행 중에 일어난다. 빌드할 때가 아니다.

증거: 실패하면 nullptr 을 준다. 빌드 때 답이 정해져 있으면 “실패”라는 개념 자체가 필요 없다. 게임모드는 .umap 안의 데이터가 정하는데, 컴파일러는 .cpp 와 .h 만 읽는다.

비트 플래그 — 스위치 4개

숫자 하나에 예/아니오 네 개를 담는 방법.

스위치값선언
Up11 << 0
Down21 << 1
Left41 << 2
Right81 << 3

켜진 스위치의 값을 다 더한 것이 directionKey 다.

왼쪽 위  =  Left + Up  =  4 + 1  =  5
왼쪽 아래 =  Left + Down =  4 + 2  =  6
오른쪽 위 =  Right + Up  =  8 + 1  =  9

왜 1·2·4·8인가 — 겹치는 조합이 없어서 합계만 보고 거꾸로 알아낼 수 있다. 5를 만드는 방법은 4+1 뿐이다. 만약 1·2·3·4였다면 4 가 “네 번째”인지 “첫째+셋째”인지 구분이 안 된다.

기호하는 일예
|스위치를 켠다areaKey |= Left;
&스위치가 켜졌나 묻는다if (directionKey & Up)

&& 와 || 를 섞지 마라. 이 파일에서 실제로 터진 버그다.

x==0 || y==0 → 테두리 전체  ·  x==0 && y==0 → 모서리 한 칸

가중치 랜덤 — 쪽지 뽑기

코드 용어를 상자와 쪽지로 바꾸면 전부 설명된다.

코드쪽지로 바꾸면
weightDownward = 4“아래” 쪽지 4장
tileUp = nullptr“위” 쪽지를 상자에서 뺀다 (탈락)
totalWeight상자에 남은 총 장수
r기계가 부른 번호
기준선 (누적합)번호표에 적힌 경계

가중치는 출발 방향이 정한다

출발한 곳의 반대쪽에 4장을 준다. 중앙으로 밀어주는 것.

directionKey = 1 (위쪽 가장자리에서 출발)

  위     0장    ← 돌아가면 안 되니까
  아래   4장    ████     가야 할 방향
  왼쪽   1장    █        가끔 옆으로 흔들리라고
  오른쪽 1장    █
        ─────
  총     6장  →  아래가 나올 확률 4/6 = 66.7%

번호표와 자

0 1 2 3  ·  아래
4 · 왼
5 · 오른

가중치가 클수록 자에서 넓은 칸을 차지한다 → 뽑힐 확률이 높다

여기에 결함이 있다

아래 4장이 탈락하면 남은 건 2장이라 기계는 0~1 번만 부른다. 그런데 번호표는 안 줄어든다.

0 1 2 3  ·  아래 (탈락)
4 · 왼
5 · 오른

기계가 부르는 번호: 0, 1  →  둘 다 주인이 없어 “살아있는 첫 주인”인 왼쪽으로 간다

결과: 왼쪽 100%, 오른쪽 0%. 의도는 50 : 50 이었다.

원인 한 줄 — totalWeight 는 탈락한 가중치를 뺐는데, 누적 기준선은 안 뺐다. 빠진 쪽지가 앞번호를 많이 차지할수록 뒷번호가 죽는다.

격자 좌표 → 배열 번호

2차원 격자를 1차원 배열 하나로 관리하는 법.

y=0 줄 :   0   1   2   3  ...  29        ← 30개
y=1 줄 :  30  31  32  33  ...  59        ← 30개
y=2 줄 :  60  61  62  63  ...  89        ← 30개
                    ↑
                x=3 이면 63

번호 = y * _mapSize + x

y * _mapSize 가 몇 줄을 건너뛰나, + x 가 그 줄에서 몇 칸 가나.

이걸 FindTile 이 대신 해주기 때문에, 부르는 쪽은 FindTile(indexX, indexY - 1) 처럼 좌표만 던지면 타일을 받는다.

칸 번호는 0부터 센다. _mapSize 가 30이면 마지막 칸은 29, 즉 _mapSize - 1 이다. 코드에 29 를 직접 쓰지 마라 — 크기가 바뀌면 전부 틀린다.

랜덤워크 한 걸음

GenerateRoadFrom 의 while 루프가 매 걸음 하는 일.

  1. 상하좌우 네 칸을 일단 다 꺼낸다 (274~277줄)
  2. 각 후보를 심사해서 안 되는 건 nullptr 로 탈락시킨다 (279~310줄)
  3. 살아남은 후보의 가중치만 더해 totalWeight 를 만든다 (312~320줄)
  4. 0 ~ totalWeight-1 중 번호 하나를 뽑는다 (322줄)
  5. 기준선과 비교해 방향을 정한다 (327~379줄)
  6. 그 칸을 길로 칠하고 이동한다 (386~419줄)

루프 밖에서 한 번만 정해지는 것 — 가중치 네 개. directionKey 가 길 하나를 만드는 내내 안 바뀌기 때문이다.

매 걸음 바뀌는 것 — indexX, indexY, lastDirection, directionStack 넷뿐이다.

심사 조건 7개

네 방향 블록이 각각 따로 있고 else 가 없다. 넷 다 실행된다. 조건은 || 로 이어져 하나만 걸려도 탈락이다.

#조건막으려는 것
①nullptr == tileUp맵 밖. 뒤 줄들을 지키는 방패라 반드시 첫 줄
②directionKey & Up출발한 쪽으로 되돌아가기
③GetType() != None이미 누가 쓴 칸 덮어쓰기
④CheckSquareForm(...)길이 2×2 덩어리로 뭉치기
⑤IsTileOutOfExpectedArea(...)담당 구역 벗어나기
⑥IsTileARoad(x, y-2)두 칸 앞이 길 — 길끼리 나란히 붙기
⑦directionStack >= 3같은 방향 3연속 — 직선이 되기

|| 는 앞이 참이면 뒤를 안 본다(단락 평가). 그래서 ①이 맨 앞이어야 한다. ③이 먼저 오면 nullptr 에 대고 GetType() 을 불러 크래시가 난다.

네 방향이 전부 탈락할 수도 있다. 막다른 골목에서 그렇다. 그때는 "No Weight" 를 찍고 break — 그 길은 중앙에 못 닿은 채 끝난다.

CheckSquareForm — 2×2 막기

한 칸씩 상하좌우로만 가도 지그재그로 돌면 네 칸이 다 찬다.

폭이 두 칸이 되면 길이 아니라 광장처럼 보인다. 그래서 막는다.

검사 방법

  1. old 와 new 가 대각선인가? 가로도 1칸, 세로도 1칸 차이
    아니면 → return false (일직선으로는 2×2가 될 수 없다)
  2. 맞으면 나머지 두 모서리를 본다. 하나는 지금 서 있는 칸이라 늘 차 있으니, 실제로는 ? 한 칸에 달렸다.
  3. ? 도 차 있으면 → return true → 부르는 쪽이 그 방향을 탈락시킨다

return true 는 “합격”이 아니다. 이 함수가 답하는 질문은 “지금 가면 2×2가 되나요?” 다. true = “네, 됩니다” = 막아라.

탈락 조건 목록(|| 체인) 안에서 불리기 때문이다.

FMath::Abs 는 절댓값이다. 부호를 떼고 “몇 칸 떨어졌나”만 본다. Abs(-1) 도 1.

이름과 뜻이 어긋난 곳

면접에서 지적할 수 있는 지점들.

IsTileARoad 는 격자 밖일 때도 true 를 준다.

“두 칸 앞”을 내다보는 용도라, 두 칸 앞이 맵 밖이면 그쪽은 막다른 길이다. 그래서 미리 막는다. 이름은 “길이냐”지만 실제 뜻은 “그쪽으로 가면 안 되냐” — ShouldBlockDirection 쪽이 의도를 더 잘 드러냈을 이름이다.

9등분 주석에 두 가지가 섞여 있다.

0b00'00 / UD'LR 은 비트 자리 설명이고 4 0 5 / 2 X 3 / 6 1 7 은 구역 번호다. 서로 무관한데 붙어 있어 areaKey 값으로 오해하기 쉽다. 실제 값은 5, 4, 6, 1, 2, 9, 8, 10 이다. 게다가 주석의 비트 순서는 실제 enum과 반대다.

조건 ②는 가중치 0과 중복이다.

directionKey & Up 이 참이면 weightUpward 는 이미 0이라 어차피 안 뽑힌다. 버그는 아니고 이중 방어다.

막혔을 때 자문할 것

지금까지 실제로 틀린 것들이다. 물어보기 전에 이 순서로 훑어라.

  • 이 함수는 뭘 돌려주나?이름 앞자리 타입이 그거다. 없으면 void.
  • 클래스 이름 붙였나?UMapGeneratorComponent:: 없으면 딴 함수가 된다.
  • 별표가 있나 없나?있으면 ->, 없으면 . — TArray<AMapTile*> 는 통에 별표가 없다. 꺼내면 생긴다.
  • 새로 만드는 건가?타입을 앞에 붙이면 “새로 만들기”. 이미 있는 건 이름만 쓴다.
  • 멤버인가 지역인가?_mapSize, _tiles 는 클래스가 이미 들고 있다. 다시 선언하지 마라.
  • return 뒤에 코드를 뒀나?실행되지 않는다. “안일 때” 코드는 if 중괄호 바깥이다.
  • = 인가 == 인가?넣는 건 =, 비교는 ==. if 안에서 = 를 쓰면 항상 참이 된다.
  • 모든 길에 return 이 있나?bool 인데 false 로 나가는 길이 빠지기 쉽다. switch 면 default: 를 확인해라.
  • 비교식을 완성했나?|| 는 완성된 비교끼리 잇는다. type == A || type == B — type == 를 매번 다시 쓴다.
  • 저장했나?check.bat 은 디스크의 파일을 읽는다. 에디터 화면이 아니다.
